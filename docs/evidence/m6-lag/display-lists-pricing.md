## 1. What a display list would have to capture

**The immediate-mode path, from `libglemu.js`.** `glBegin` saves the client-attribute state, zeroes `GLImmediate.vertexCounter` and points `GLImmediate.vertexData` at `GLImmediate.tempData`, one `Float32Array` over a buffer of `GL_MAX_TEMP_BUFFER_SIZE` = 2,097,152 bytes (`settings.js`). Every attribute call is a wasm→JS call that appends to that array in call order and registers a component with `addRendererComponent`, which accumulates one interleaved stride for the whole block: `glVertex3f` writes 4 floats (16 B), `glTexCoord2f` 2 floats (8 B), `glColor4f` inside a block one slot of 4 packed bytes (4 B); a `glColor4f` outside a block only sets `GLImmediate.clientColor`. `glEnd` runs `prepareClientAttributes(count, true)`, sets `firstVertex`/`lastVertex`, then `GLImmediate.flush()`. `flush` is where everything happens: `getRenderer()` picks or compiles the fixed-function shader from a key made of the enabled attribute set, fog mode, clip planes, lighting and lights, alpha-test function, `GL_POINTS` or not, the current program, and `TexEnvJIT.traverseState` (per texture unit: which texture targets are enabled plus the env keys); `GL_QUADS` (mode 7) is rewritten to `TRIANGLES` over `tempQuadIndexBuffer`; then `renderer.prepare()` binds a temp VBO (`GL.getTempVertexBuffer(end)`), uploads `vertexData[firstVertex*stride .. lastVertex*stride]` with `webglBufferSubData` — this upload is exactly what the harness's `kb_per_frame` sums — re-sends the modelview/projection matrices only if their `matrixVersion` moved, sets `vertexAttribPointer` for position, normal, texcoords and colour (or a constant `clientColor` when the block carried none), pushes fog/clip/light/alpha uniforms, and finally `drawElements`/`drawArrays` — one per flush, which is what `draws_per_frame` counts. `glDrawArrays`/`glDrawElements` go through the same `flush`.

**What is read at flush time and what is not in the emulation's hands at all.** Read at flush: the vertex bytes and layout, the mode, the two matrices (by version), and the FFP key state above. Not tracked by `GLImmediate` at all: the bound texture (`glBindTexture` lives in `libwebgl.js` and goes straight to `GLctx.bindTexture`), blend, depth mask, polygon offset — those pass straight to WebGL and are simply whatever is set when the draw is issued. `glEnable(GL_TEXTURE_2D)` is special: `GLEmulation`'s `glEnable` returns early for it and only `TexEnvJIT.hook_enable` records it, nulling `currentRenderer` so the next flush re-keys the shader.

**What `rDisplayList.cpp` expects of the five entry points.** `rDisplayListFiller::Start`: records only if `sr_useDisplayLists != rDisplayList_Off`, `inhibit_ == 0` and no other filler is live (`sr_currentFiller`) — one list at a time, tree-wide; allocates with `glGenLists(1)` and opens `glNewList(list, sr_useDisplayLists == rDisplayList_CAC ? GL_COMPILE : GL_COMPILE_AND_EXECUTE)`. So **`rDisplayList_CAC` is "compile, then call"**: `GL_COMPILE` captures without drawing and `Stop()` issues `list_.Call()` itself right after `glEndList` (`rScreen.h`'s enum comment says the same); `rDisplayList_CAE` is the mode that draws while recording. (The plan's Step 1 brief had these the other way round; the code is as stated here.) `rDisplayList::OnCall` returns false while any list is recording — nested draws get agglomerated into the outer list — and otherwise `glCallList`s. `Clear()` during a fill is deferred through `inhibit_`; `Cancel()` is `Clear(0)` + `Stop()` on the live filler, and is called by `rModel::Render` whenever a model has no list ("model display lists should definitely be compiled before other lists") and by `rTexture` when a texture is generated mid-record; `ClearAll()` runs on screen-mode change (`rCallbackBeforeScreenModeChange`), texture reload and movie-pack switch. `glDeleteLists` is only ever reached with `filling_` false. `tASSERT( list_.list_ )` after `glGenLists` is compiled out: `tError.h` defines `tASSERT(x)` as nothing without `DEBUG`, and `web/Makefile`'s `BASE_CXXFLAGS`/`CLIENT_DEFS` carry no `-DDEBUG` — `eCompat.cpp`'s own comment says so and is right; the plan's reconnaissance item 5 ("would trip `tASSERT`") is not.

**What the wall list actually contains.** `gCycleWallsDisplayListManager::RenderAllWithDisplayList`, per cycle per frame, does `dir_eWall_select()` (the texture bind) and `glDisable(GL_CULL_FACE)` *outside* the list, decides whether to `Clear(0)` (tail expired, or `wallsWithPossibleDisplayList >= 3`, or five times the new count exceeds `wallsInDisplayList_`), then `displayList_.Call()`; on a miss it opens `rDisplayListFiller filler( displayList_ )` and calls `RenderAll( camera, cycle, wallsWithDisplayList_ )`, which *inside* the list issues `sr_DepthOffset(true)` (`glPolygonOffset` + three `glEnable`s), `glDisable(GL_TEXTURE_2D)`, one pass of every wall in `gWallRenderMode_Lines`, `RenderEnd()`, `sr_DepthOffset(false)`, `glEnable(GL_TEXTURE_2D)`, one pass in `gWallRenderMode_Quads`, `RenderEnd()`. Per plain segment `RenderNormal` emits 2 × (`glColor4f` + `glVertex3f`) in the lines pass and 4 × (`glColor4f` + `glTexCoord2f` + `glVertex3f`) in the quads pass: 16 wasm→JS calls and 40 + 112 = 152 bytes, every frame. Because `glRenderer::BeginPrimitive` makes a `Begin*()` a no-op while the same primitive is current and `RenderList` never calls `RenderEnd` between walls, **all of a cycle's plain walls batch into one `GL_LINES` block and one `GL_QUADS` block per pass**; only the head wall's `RenderBegin` (`BeginLineStrip`/`BeginQuadStrip`, force-ended) and the split between `wallsWithDisplayList_` and `wallList_` add draws — a handful per cycle, not one per segment. Walls whose head is still within `gBEG_LEN` of the cycle call `ClearDisplayList()` and stay out of the list via `displayListInhibition_`; the `currentWall` is inhibited for two frames (`ClearDisplayList(2)`).

**Replay semantics a list must honour, from the GL spec as this code uses it.** `GL_COMPILE` stores *values*: the colours and texcoords are in the vertex stream, the enables and polygon offset are commands in the list. `glCallList` runs under the *current* matrices (the camera has already set modelview for this frame; wall vertices are world-space, so replay is correct) and the *current* bound texture (set outside the list by `dir_eWall_select()`). The §10 hazard (`docs/porting/browser-runtime-notes.md`) carries straight over: the lines block is a 20-byte `{COLOR, VERTEX}` format and the quads block a 28-byte `{COLOR, TEXTURE0, VERTEX}` format — a replay must keep them as separate draws with their own strides; concatenating them into one buffer draws garbage or trips `assert(numVertices % 1 == 0)`.

**Other owners of an `rDisplayList` in the client** (what counted: `rDisplayList`/`rDisplayListAlphaSensitive` members and statics, by grep): `gCycleWallsDisplayListManager::displayList_` (walls), `rModel::displayList_` (every model, including the cycles — `rModel::Render`'s immediate-mode branch runs per model per frame today), `se_rimDisplayList` (`eAdvWall.cpp`, the rim), `gHud.cpp`'s two `list_` caches, `sr_consoleDisplayList`, and `gWinZone.cpp`'s `zoneList`. `gFloor.cpp` and `gSparks.cpp` own none. So the plan's "cycles, floor and HUD are not [cacheable]" is two-thirds wrong: models and HUD are list-able by the same mechanism; the floor and the sparks are not.

## 2. Two implementation shapes, costed

### (a) In `eCompat.cpp` — the finding is that there is no hook

`GLImmediate.flush` is a method on the `$GLImmediate` JS library object, reached only from `glEnd`, `glDrawArrays` and `glDrawElements` inside `libglemu.js`. No C-callable symbol exposes it, nothing in C++ can observe when a batch is laid out or uploaded, and `eCompat.cpp` cannot wrap `glVertex3f`/`glColor4f`/`glTexCoord2f`/`glEnd` either — those are the JS library's own exports and this file may only define what the link reported undefined (its header says so; a `-Wl,--wrap` route is unverified here). The only C++-side design left is an *entry-point command list*: real bodies for the five stubs that, between `glNewList` and `glEndList`, would need the game's calls diverted into a buffer — which they cannot be from this file — and, at `glCallList`, re-issue `glBegin`/`glColor4f`/`glTexCoord2f`/`glVertex3f`/`glEnd` to the emulation. Even granting the diversion, replay pays every per-vertex wasm→JS call, the same `flush`, the same `bufferSubData` upload and the same draw as today; what it saves is the C++ side of `RenderList` (the `coords_` loop, `Alpha()`, the length cut), which Task 3 did not price and which is not in the render part it did price. Files: `eCompat.cpp` (and `web/Makefile` if wrapping); rough size 150–250 lines; `-sASSERTIONS=1` interaction: none new, every emulation assert stays live. Three riskiest semantics — record-vs-replay state (a C++ recorder sees `glEnable`/`glPolygonOffset` only if it wraps those too), CAC (a `GL_COMPILE` fill must *not* draw, so the recorder must swallow the fill's vertices, the opposite of what the stubs do today), and `Cancel()` mid-fill — are all real and all buy nothing, because the shape does not touch the priced cost. **Not worth building.**

### (b) A JS library override, recording at the point the emulation already has the batch

`modules.mjs` appends user `--js-library` files after every system library "so that users can override built-in JS library symbols" — so a `web/library_displaylists.js` linked from `CLIENT_LDFLAGS` can define the five names (the stubs leave `eCompat.cpp`, which is on `CLIENT_OBJS` only and not on the dedicated link line, so the dedicated wasm's 2,488,298 bytes / `9718a2a6…` are untouched by construction) and, with `__deps: ['$GLImmediate']`, wrap `GLImmediate.flush` and a short whitelist of state entry points. Record: while a list is open in `GL_COMPILE`, `flush` copies `vertexData.subarray(firstVertex*stride/4, lastVertex*stride/4)` plus `{mode after the QUADS rewrite, stride, the live attribute layout (name/size/type/offset), numVertices, numIndexes}` into the list and returns without drawing; whitelisted `glEnable`/`glDisable`/`glPolygonOffset`/`glBindTexture` calls are appended as commands; any *other* GL call during recording aborts with a named message under `ASSERTIONS` so a gap in the whitelist is loud, not silent (the rim list needs `glEnable(GL_DEPTH_TEST)`, `glDisable(GL_CULL_FACE)` and a texture `Select()`; the wall list needs the offset and texture toggles listed in §1). Replay at `glCallList`: for each batch, restore `GLImmediate.vertexData`, `liveClientAttributes`/`clientAttributes`/`enabledClientAttributes`, `stride`, `mode`, `firstVertex`/`lastVertex`, null `currentRenderer`, and call the original `flush` — so matrices, bound texture, fog and alpha test are the current ones (GL semantics) and shader selection is the emulation's own. The cheap version re-uploads each batch from the temp buffer every call (bytes saved: none; JS calls saved: all 16 per segment); the version that actually removes the upload keeps a persistent WebGL buffer per batch and binds it as `GLctx.currentArrayBufferBinding` with offset-0 layout — and that is where the riskiest semantic lives: `GL_UNSAFE_OPTS` defaults to true (`settings.js`) and `renderer.prepare()`'s `canSkip` heuristic compares `lastRenderer`, `lastArrayBuffer`, `lastProgram`, `lastStride` and `matricesModified` to skip attribute setup; a replay that binds its own buffer must keep `GLImmediate.lastArrayBuffer` coherent or call `lastRenderer.cleanup()` before and after, or the next immediate-mode flush reads attributes off the list's buffer ("try disabling GL_UNSAFE_OPTS if you have odd glitches" is the emulation's own warning). The other two: CAC — prefer `rDisplayList_CAE` for the first cut, since "draw during the fill, also remember it" is one increment on what the stubs do today, whereas `GL_COMPILE` must swallow every flush of the fill and `rDisplayListFiller::Stop` then replays immediately; and deletion/cancel — `rDisplayList::Cancel()` fires from `rModel::Render` and `rTexture`, so a half-recorded list must be discardable and `glDeleteLists` must free the WebGL buffers (and `ClearAll` on screen-mode change frees every one). `-sASSERTIONS=1`: replay goes through the real `flush`, so `numVertices` integrality and the 2 MB `too much vertex data` assert stay live; a temp-buffer replay inherits the 2 MB ceiling per batch (18,724 quad segments at 112 B; a persistent buffer does not). Files: new `web/library_displaylists.js` (~250–400 lines), `web/Makefile` (one flag), `eCompat.cpp` (−5 stubs, +a comment), `web/webdefaults/autoexec.cfg` (its `USE_DISPLAYLISTS 0` hard override becomes a default or a `?dl=` switch). Gating: `USE_DISPLAYLISTS` stays the runtime `tConfItem` (`rModel.cpp`), the NVIDIA probe stays compiled out (`rScreen.cpp`, `#if defined( DEDICATED ) || !defined( __EMSCRIPTEN__ )`), and the menu entry in `gMenus.cpp` already exposes Off/CAC/CAE. Rebuild cadence is set by the manager: a cycle's list is rebuilt whenever three new list-able walls accumulate, and a rebuild costs one full immediate-mode pass for that cycle — a few times a second across eight cycles, so the amortised saving is most but not all of the per-frame cost.

## 3. The ceiling, with the arithmetic

What lists could remove is bounded by the render part (`ms_first_draw_to_swap`) of the late frame, and within it by the list-able objects. Task 3's numbers, all cpu 6, `MAX_FPS 1000`:

| scene | draws/frame | KB/frame | render part | frame p50 |
|---|---|---|---|---|
| baseline flat late window (7 of 10 rounds, `SP_SIZE_FACTOR 6`, 7 AIs) | 111–115 | 179–182 | 15.4–18.7 ms | 24.5–28.0 ms |
| grind, free driving (0.5× arena, 0 AIs, one trail) | 52–55 | 40 | 4.6–6.3 ms | 11.1–11.4 ms |
| difference | ~60 | ~140 | **10–13 ms** | — |

- **Upper bound.** 10–13 ms of a 24.5–28.0 ms flat late frame: 36–53 %, "about half", as Task 3 read it. That difference is not walls alone: Task 3 names four 400-unit trails and a floor 8× as wide; the code adds seven more cycle models through `rModel::Render`'s immediate-mode branch. Of the three, walls and models are list-able and the floor is not. **Walls alone are not measured**, and two settings-only arms in the same arena would split them: one with trails made negligible (`SP_WALLS_LENGTH` small) and one with `SP_NUM_AIS 0` — Task 4's harness, no source change.
- **Per-frame cost the list removes, mechanically.** Sixteen wasm→JS calls and 152 bytes of upload per plain segment per frame, and the `flush` work per pass. It does *not* remove draw calls for plain walls: they already batch into one lines and one quads draw per cycle per pass (§1). So Task 3's 24–47 µs per *extra draw call* is not the wall coefficient; the wall coefficient is per byte and per vertex, and `kb_per_frame` is its instrument. A replay still costs at least one bind, attribute setup and draw per batch — not zero.
- **What actually grew.** In the seven flat rounds the late-window growth was 1.0–4.4 ms with the render part a median 0.4 ms of 3.6 and the pre-draw part (simulation) 2.7: lists cannot touch the 2.7. In the three spike rounds the render part rose 9.6–17.0 ms with +286 to +404 draw calls, and since plain wall segments cannot add draw calls, those spikes are not batched wall geometry; what they are is not settled (Task 3 says so), but no object that produced them is known to own a list, and `gSparks.cpp` — whose bursts the grind measured at +110 draws — owns none. Mechanism 2's +2.5–3.2 ms at the wall is pre-draw and untouched.
- **Ceiling stated.** X ≤ 36–53 % of a flat late frame as an unsplit upper bound over walls, models and floor together; of the *growth* the maintainer feels, the part a wall list could remove is a median 0.4 ms of 3.6 in the ten rounds measured. On the phone's real boot path — post-tutorial, `SP_WALLS_LENGTH` −1, trails that never expire — the wall share can only be larger, and no arm has measured that path.

## 4. Go / no-go

**Not yet.** Shape (b) is buildable and the only shape that touches the priced cost, but at 250–400 lines in the layer that produced M2's largest defect class (§10) plus the `GL_UNSAFE_OPTS` bookkeeping, it is a milestone with its own gate, and the number that would justify it does not exist: Task 4 has not measured the cheap levers it must beat; the ten baseline rounds put the render part's share of the late frame at a median 3.1 % and the median growth in the simulation, which no list touches; and the one scenario where a wall list's benefit grows with driving time — the unlimited-trail boot path — has never been an arm. Build it if, and only if, a same-arena split shows walls alone at ≥ 5 ms of a flat late frame at rate 6 on that boot path and growing; if `SP_WALLS_LENGTH` in Task 4 removes the same milliseconds for a gameplay cost the maintainer accepts, no-go — a length cap takes the geometry out of both the renderer and the grid, a list takes it out of the renderer only.

## 5. The one experiment worth running, described and not run

Append `USE_DISPLAYLISTS 1` through the harness's `CONFIGLINES` (it lands after the file's own `USE_DISPLAYLISTS 0`, `arm.steps.tmpl` writes `cur+add`). With the stubs as they are, every fill draws straight through and `Call()` never succeeds, so the frame is drawn as today — with three differences the reader of that arm must know: `rDisplayList::IsRecording()` is true during each fill, so `eWallRim::RenderAll` passes a null camera and `gWallRim::RenderReal` skips its "shadow" quads, any other list's `OnCall` returns false meanwhile, and `rModel::Render` fires `Cancel()` on every model without a list. A one-line counting stub in `glGenLists` (client-only file, dedicated bytes unaffected) logging fills per second would say how many `glCallList` sites would fire per frame with lists on — the count the plan asks for — but it is a `src/emscripten` change and therefore Task 6's to make, not Task 5's; `rDisplayList.cpp`'s `LIST_STATS` counter already does this natively under `DEBUG`. The two split arms in §3 need no source change at all and are the better first spend.

## What the two drafts disagreed on

Both drafts arrived empty — "(missing)" in place of Draft A and Draft B — so there were no draft-level disagreements to adjudicate, and nothing in this note is carried forward from either; every claim was read from the files named at the top. The disagreements that *were* resolved are between the plan's Task 5 brief (and Task 3's README) and the code, and are worth the maintainer's eye: (1) `rDisplayList_CAC` is `GL_COMPILE` then an explicit `Call()`, not `GL_COMPILE_AND_EXECUTE` — `rDisplayListFiller::Start` and `rScreen.h`; (2) forcing `USE_DISPLAYLISTS` does not trip `tASSERT( list_.list_ )` in this build — `tError.h` under no `DEBUG`; (3) "cycles, floor and HUD are not cacheable" — `rModel` and `gHud` own lists, `gFloor` and `gSparks` do not; (4) plain wall segments do not each cost a draw call — `glRenderer::BeginPrimitive` merges them into one block per cycle per pass, so the per-draw coefficient is not the wall coefficient; (5) Task 3's "four trails plus the floor" for the 10–13 ms omits the seven extra cycle models in the baseline scene.
