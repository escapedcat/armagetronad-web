# THE STEERING DIFFERENTIAL. One template, two arms, and the difference
# between them is the whole measurement. web/tools/run-steer-arm.sh substitutes
# the arm-name marker with the arm's name and the input marker -- the only line
# in this file that is nothing but a marker -- with that arm's input program.
# Run that script, not this file.
#
# THE MARKERS ARE NOT SPELLED OUT ANYWHERE IN THIS COMMENT, AND THAT IS
# DELIBERATE. The first cut of this file named them here, the substitution hit
# the comment as well as the body, and the input program landed in the middle
# of a comment paragraph -- which broke the leading # on the following line and
# fed the driver `shot:...180s with its input program by ...` as its first
# step. The driver's own error was `Page.captureScreenshot: Not attached to an
# active page`, i.e. it fired a screenshot before the page had loaded, which
# points nowhere near the real cause. run-steer-arm.sh now substitutes the
# input marker only on a line that consists of nothing else, and checks every
# generated body line against the driver's verb list before running it.
#
# WHAT THIS ANSWERS AND WHY IT NEEDED A NEW INSTRUMENT.
# web/tools/bridge-gate.steps already proves, from the server's own log, that a
# browser player logs in, joins the roster, plays and dies. It does NOT prove
# that a steering keypress reached the server, and it says so in as many words.
# Nothing in this tree logs per-turn state: there is no position ladderlog
# entry and no per-turn one -- the writers are enumerated at
# src/tron/gGame.cpp:3130, src/tron/gCycle.cpp:3236, src/engine/ePlayer.cpp:6555
# and src/engine/eTeam.cpp:220, and none of them fires on a turn. And the two
# obvious substitutes are both dead ends: a round's duration is set by when the
# AIs finish, not by the browser player, and gCycle::KillAt credits a death as
# suicide whenever no enemy influence is attributed (src/tron/gCycle.cpp:3276),
# which covers the rim and one's own wall alike.
#
# SO THE INSTRUMENT IS THE SERVER'S OWN SIMULATION CLOCK, AND THE ARENA IS
# EMPTIED SO THAT CLOCK MEANS SOMETHING.
# bridge/test-server/steer-var/autoexec.cfg turns off the AIs, so the arena
# holds exactly one cycle: the browser player's. The only things that can kill
# it are the rim and its own wall. It also sets LADDERLOG_GAME_TIME_INTERVAL,
# which makes the server write `[L] GAME_TIME <t>` every 0.25 s with
# se_GameTime() -- its own clock, reset each round -- so the server's own
# `[L] DEATH_*` line for web_user is timestamped on the server's clock.
#
# THE OBSERVABLE IS THEREFORE: how long, in SERVER game-seconds, the server's
# copy of the browser player's cycle stayed alive.
#
# A cycle that never turns drives straight from its spawn point to the rim and
# dies there, after an interval fixed by the arena and the cycle's speed. That
# is an UPPER BOUND on how long a non-steering player can survive, and the
# control arm MEASURES it rather than assuming it -- several rounds of it, so
# its spread is a reading too. The steering arm then has to beat that bound.
#
# WHY BEATING IT IS PROOF AND NOT A CORRELATION. The server simulates the
# cycle. If a turn command never arrived, the server's cycle went straight and
# died at the rim, whatever the browser's own screen was showing. For the
# SERVER's clock to record a longer life, the SERVER's cycle must have turned,
# and the only thing that turns it is a turn command over this socket. The
# client cannot fake the reading either: it is `docker logs aa-server`,
# collected after the browser is gone.
#
# WHAT IT STILL DOES NOT PROVE: which keypress, or how promptly. This is a
# yes/no on arrival, not a latency measurement.
