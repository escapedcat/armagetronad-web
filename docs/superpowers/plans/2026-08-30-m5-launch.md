# M5 — Validation, packaging, launch

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Demo is publicly reachable and playable at a GitHub Pages URL, in Chrome and Firefox.

**Architecture:** No new subsystems. One-line fix to a live crash, one link-flag change, one HTTPS-only behaviour to handle, a deploy, and a gate that runs against the *public* URL rather than a local server.

**Tech Stack:** Unchanged — Emscripten 6.0.8, SDL 1.2 emulation, Asyncify, `-lidbfs.js`. Deploy via `npx gh-pages`.

## Global Constraints

- **`make -f web/Makefile dedicated` must still produce EXACTLY 2,488,298 bytes AND md5 `9718a2a64978cb6e9b95ea2f0454cca5`.** **Size alone is not sufficient** — M4 task 3 measured an unguarded build hitting exactly that size with a different md5. *A live example is sitting in this repo: the main checkout's stale `dist-m0` artifact had the right size and md5 `a1043e83…`. It has been deleted; rebuild before trusting any artifact you did not just make.*
- Verify object identity by compiling with the same flags to a scratch location and comparing md5. **Hold the source basename constant — the `-o` path is irrelevant.** A control that copies source to a scratch *filename* measures the rename.
- **A control link must substitute objects in place, never append** — object order moves the output by hundreds of bytes.
- Guard game-source changes: `#ifdef __EMSCRIPTEN__`, or `#if !defined(DEDICATED) && defined(__EMSCRIPTEN__)` where the file also compiles into the dedicated build.
- New files ONLY under `src/emscripten/`, `web/`, `deps/`, `docs/`.
- **Same-file citations in comments name a symbol, not a line number.**
- **Any sentence that counts or enumerates is suspect until checked**, and if you state a count, say what basis you counted on. Eight such errors were caught in M4 alone.
- **Commit messages containing backticks must use `git commit -F <file>`** — inline `-m` runs them as shell command substitution and silently empties them.
- No automated test suite exists and none is to be created. Verification is command output and browser evidence.
- Work in `.worktrees/m5-launch` on branch `m5-launch`. Commit after every green step.

## What reconnaissance established — do not rebuild these assumptions

All measured at `109beea9`, not inferred.

1. **`-O` and `ASSERTIONS` are separable, and this was proven by *firing* the assert, not by reading flags.** `-O2 -sASSERTIONS=1` links (4,331,084 B; assertions cost 5.1% over bare `-O2`). The §10 assert aborts identically on the no-`-O` build and on `-O2 -sASSERTIONS=1`; on **bare `-O2` it silently renders wrong geometry instead**. The committed sweep re-run reports the same 19 sites §10 already adjudicates — no new ones. **So M2's ban on `-O` was really a ban on losing ASSERTIONS, and the size work is unblocked.**
2. **`rViewport.cpp`'s §10 site is NOT latent. It is a live crash four keystrokes from the main menu.** Main Menu → Player Setup → Down×4 highlights "Viewports: Single Player" and the tab dies with `Assertion failed: numVertices must be an integer`. It is in `RenderBackground()`, so *highlighting* is enough — no selection required. Every milestone since M2 has called this latent. It is not, and it would ship.
3. **Size is already won.** Today's wire total is **4,097,685 B gzipped (≈3.91 MiB)** against `PLAN.md`'s 15 MB budget — met by 3.6× with **no `-O` at all**. `-O2 -sASSERTIONS=1` takes it to **1,707,733 (≈1.63 MiB)**. `-O2`/`-O3`/`-Os`/`-Oz` differ by **10,728 bytes on the wire (0.9%)**, and the raw-size ordering *inverts* under gzip — **do not spend time choosing**; `-O2` is emcc's safe default.
4. **GitHub Pages serves gzip only.** Measured on bare `*.github.io` hosts: `Accept-Encoding: br` alone returns identity. It serves `.wasm` as `application/wasm` and gzips it, and gzips `application/octet-stream` too, so `.data` compresses. **Brotli is worth 378,988 B (22%) and needs a custom domain proxied through Cloudflare — not worth it. Drop the brotli work.**
5. **JSPI links and is much smaller, but it costs M3.** Both target browsers boot `-fwasm-exceptions -sASYNCIFY=2` at 1,751,966 B (−80%), but **audio dies**: Emscripten 6.0.8's `libsdl.js` pushes to `Asyncify.sleepCallbacks` under `#if ASYNCIFY`, while that array exists only under `#if ASYNCIFY == 1`. `-fexceptions` + JSPI dies before `main`. **Declined for M5** — recorded so nobody re-explores it.
6. **`PLAN.md` under-reports `-fexceptions` on the client by 1.58 MB.** It quotes +827,185 B; that is the **dedicated, non-Asyncify** figure from M0, and `web/Makefile` says so in its own comment. On the client at HEAD it is **+2,402,246 (+37.1%)** — exceptions and Asyncify multiply, because Asyncify instruments the unwinder too. Asyncify's own +5,893,427 (+197.4%) **does** hold, against M2's +5,888,604.
7. **The multiplayer menu behaves differently over HTTPS, and Pages is HTTPS-only.** Route is Play Game → Multiplayer (not on the main menu). Over `http:` — 5 failed `ws://master*` attempts, then the game's own "Sorry, no server found :-(". Over HTTPS — same screen, but **97 blocked mixed-content retries in 26 s**. **No local gate has ever exercised this**, because every gate to date served over `http:`.
8. **The deploy is four files, 10.2 MB, all asset URLs relative** — sub-path hosting was measured by serving every test from a subdirectory, not assumed. No COOP/COEP needed; nothing underscore-prefixed. **Entry point is `armagetronad.html`, not `index.html`.** `npx gh-pages` keeps history by default — use `-f --nojekyll`.
9. **One Pages fact remains unmeasured:** whether the edge gzips a file larger than ~4 MB. The largest compressible asset findable on any `*.github.io` host was 2.2 MB (and it *was* gzipped). It costs one deploy and one `curl -I` to settle, and **the deploy step must not skip it**.

### Task 2b: The camera — make the Demo look like Armagetron

**Files:** Modify `src/emscripten/eCompat.cpp`; create evidence under `docs/evidence/`

**Interfaces:** Consumes Task 2. Produces a client with a working 3D view.

**Added mid-milestone at the maintainer's request**, after they noticed every browser screenshot shows a top-down view and asked whether it was known. It was — §11, since M2 — but it had been carried as a footnote through four milestones while the Demo's entire pitch is "play Armagetron in your browser". **A permanently top-down view in which the player's own bike sits just outside the frame is arguably this port's largest quality defect, and §11 records the fix as small.** Executed after Task 2, before Task 3.

- [ ] **Step 1: Confirm the diagnosis before writing the shim**

`docs/porting/browser-runtime-notes.md` §11 says Emscripten's `gluLookAt` calls the bundled gl-matrix's `mat4.lookAt`, which is declared `(eye, center, up, dest)` — **destination last** — while Emscripten passes destination **first**. So the current matrix arrives as `eye`, the real eye as `center`, and the sixteen-float result is written into the three-element array literal `[ux, uy, uz]` and discarded. **The current matrix is read and never written.** `gluPerspective` eight lines above assigns its result back correctly, which is why this reads as a plain bug rather than a design choice.

Verify that argument-order claim against the bundled `gl-matrix.js` in *this* emsdk before relying on it. §11's line citations may have drifted — it is an emsdk file, and this project's convention is that emsdk citations are paired with greppable tokens for exactly that reason.

- [ ] **Step 2: Implement `gluLookAt` in `eCompat.cpp`**

The same way that file already shims `glRectf` and the display-list stubs. It must compose correctly with what the game does around it: `eCamera::Render` sets the whole view orientation with one `gluLookAt` on the **projection** matrix, followed by `glTranslatef(-pos.x, -pos.y, -z)`. Read that call site before choosing where your result lands.

**This is new behaviour, not a bug-for-bug port** — §11 flags that explicitly. Say what you implemented and against which reference.

- [ ] **Step 3: Verify visually, because that is the only verification that means anything here**

§11 gives three measured signatures of the broken state, all from M2 gate frames — use them as the before/after: the floor grid shows **no perspective convergence**; a cycle's wall projects to a **one-pixel vertical line at x = 511** on a 1024-wide canvas (exactly screen centre); and the default `CAMERA_CUSTOM`, ≈13.5 units behind at ≈10 up, puts the cycle **just outside the frame**, reappearing only if the camera is moved to ≈3 units back.

After the fix, all three should change: convergence visible, the wall no longer a centre line, and **the bike visible in frame at the default camera**. Screenshot both browsers. `CAMERA_IN` is **not** an acceptable substitute — `eCamera.cpp` removes the centred object from the render list within 1 unit.

- [ ] **Step 4: Check the other half of §11 and decide, do not silently skip**

§11's second half: `default.cfg` binds `LOOK_LEFT`/`LOOK_RIGHT`/`BANK_UP`/`BANK_DOWN`/`ZOOM_IN` to keycodes 324–336, which are this program's own mouse pseudo-keys `SDLK_LAST+1…+13`. **SDL 1.2's `SDLK_LAST` was 323; in this build it is 1536**, so those binds are dead. With the camera working, they become meaningful for the first time. Say whether M5 fixes them or defers them, and why.

- [ ] **Step 5: Verify invariants and commit.** Dedicated wasm **2,488,298 bytes AND md5 `9718a2a64978cb6e9b95ea2f0454cca5`** — `eCompat.cpp` is client-only, so this should be structural; confirm with the substitute-in-place control rather than asserting it. Re-run M2's gameplay gate: the camera change alters every rendered frame, and that gate is the one that would notice.
