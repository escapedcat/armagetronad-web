## Known landmines — established by reconnaissance, measured not inferred

1. **`fill_audio` runs at the completion of every Asyncify *rewind*, with wasm on the stack.** Measured: `Asyncify.state == Normal` in 750/750 samples, `exportCallStack.length == 3` in 720. **Nothing reachable from it may sleep *or throw*** — `callUserCallback` turns an escaping exception into a process abort.
2. **Therefore: do NOT simply delete the `Load()` short-circuit.** `PLAN.md`'s M3 note says "that block is M3's to delete", and that is wrong — deleting it re-arms `throw tGenericException` in **`eWavData::Load`** (~~`eSound.cpp:488` and `:500`~~ — those line numbers rotted during M3 itself; the file now states the rule that same-file references name a symbol), which is fatal on the `fill_audio` → `Mix` → `Load()` path. **Replace the guard, do not remove it.** *Confirmed under execution and the single most valuable line in this plan: it is the one that stopped Task 1 from shipping a process abort. `PLAN.md`'s M3 note now carries the retraction inline.*
3. **`SDL_LoadWAV_RW` cannot be implemented in C.** Emscripten's `SDL_RWFromFile` returns a *JS array index*, not a struct (`libsdl.js:3543-3550`), and never fails. Write the parser behind `eSound.cpp:407`'s own static `SDL_LoadWAV(char const*, …)` and `fopen` directly.
4. **No format conversion is needed.** Both WAVs are **8-bit unsigned mono PCM** — `cyclrun.wav` at 22050 Hz, `expl.wav` at 11025 Hz with a trailing `LIST` chunk. `eSound.cpp:510-514` skips conversion for `AUDIO_U8`, and the mixer resamples itself (`:668-669`). The parser is ~50 lines, not the ~80 `PLAN.md` estimated.
5. **`SDL_BuildAudioCVT` and `SDL_ConvertAudio` stay unreachable and should keep returning −1.** `PLAN.md` says M3 "must make [all three stubs] reachable again"; only `SDL_LoadWAV_RW` changes status, and it changes to *deletable*. The one mandatory `eCompat.cpp` edit is `SDL_FreeWAV` → `free()`.
6. **Autoplay already works — `web/shell.html` needs no change.** Measured: a *trusted* click gives `hasBeenActive: true`, `audioContext.state: "running"`, **zero** warnings; a synthetic click gives `false` / `"suspended"` / **five**. M2's five `AudioContext was not allowed to start` warnings were a **harness artifact** — `drive-browser.mjs:362-371` clicks via `Runtime.evaluate`, which is not a user gesture.
7. **`SOUND_BUFFER_SHIFT 3` costs 0.974 s of latency.** Measured: 4096 samples / 185.8 ms / 0.974 s, versus shift 0's 512 / 23.2 ms / **0.184 s** — with zero starvation at either, including through a real round. `PLAN.md` recommends 3; that is close to a second of audio lag on a game about reflexes.

   > **HELD, but it does not choose the value — Task 2 had to add the missing half.** Zero starvation at *every* value 0–3 means starvation cannot decide, and this recon was taken with a callback that only `memset`s, so it contains no mixing work at all. What decides is margin: latency and starvation tolerance are the **same quantity** (`bufferingDelay + numSimultaneouslyQueuedBuffers × bufferDuration`), so you cannot buy one without paying the other. Against a worst observed main-thread stall of 119–142 ms, shift 0's 162 ms is ~1.1–1.4× and shift 1's 278 ms is ~2.0–2.4×. **M3 ships `1`.** Also note why upstream's own default of 0 does not transfer: native SDL 1.2 runs `fill_audio` on its own audio thread, where a stalled main thread costs the device nothing; Emscripten has one thread, so every main-thread stall *is* an audio stall.
8. **Every `eWavData` names a moviepack file first and a `sound/` file as fallback**, and `moviesounds/` **does not exist in this tree and is not preloaded** (`gCycle.cpp:230-232`, `gExplosion.cpp:38`; the preload list in `web/Makefile` covers `sound/` but not `moviesounds/`). So the *missing-file* path runs on every single load, before any successful one. Whatever the parser does when `fopen` fails is therefore the common case, not the edge case — and per landmine 1 it must fail without throwing. Confirmed by the controller: both formats are exactly as reconnaissance measured (`fmt=1 ch=1 rate=22050 bits=8` and `rate=11025`, plus a 66-byte `LIST` chunk in `expl.wav`), and only two distinct `sound/` files are referenced across all four `eWavData` constructions.

   > **CORRECTED BY TASK 1 — the sentence above undercounts.** There are **six** `eWavData` constructions, not four: `gCycle.cpp:230-232` (`cycle_run`, `turn_wav`, `scrap`), `gExplosion.cpp:38` (`explode`), and `gGame.cpp:181-182` (`intro`, `extro`). The "two distinct `sound/` files" half is still true — `sound/cyclrun.wav` and `sound/expl.wav` are the only real files — but the two `gGame.cpp` ones were missed, and they matter because they name a moviepack file with **no `sound/` fallback**, so they take `Load()`'s *other* retry arm.
   >
   > That arm is a landmine of its own, and it is **upstream code, not ours**: `eSound.cpp:815` loads `sound/expl.wav` as a stand-in and then deliberately sets `len = 0`. The result is a wav with `data != NULL` and `samples == 0` — upstream's silent-placeholder idiom. `eWavData::Mix`'s `while (goon)` (`:1017`) can never exit on that shape when `loop` is true: the inner loop cannot advance with `samples == 0`, `pos.pos >= samples` is then always true, and `pos.pos -= samples` subtracts nothing, so `goon` never goes false (`:1137-1140`). That is an infinite loop **inside the audio callback** — a frozen tab, not a muted one.
   >
   > **Latent, not live**, and Task 2 should keep it that way: `eSoundPlayer`'s `loop` defaults to false (`eSound.h:112`) and `gGame.cpp:4530-4531` construct `introPlayer`/`extroPlayer` with that default, so `goon` goes false on the first pass today. The only looped sound is `cycle_run`, which loads successfully. It is one config change from live.

### Task 1: Load a WAV

**Files:** Modify `src/engine/eSound.cpp`, `src/emscripten/eCompat.cpp`

**Interfaces:** Produces a client that can load `cyclrun.wav` and `expl.wav` into memory. Sound may not be audible yet — Task 2 owns the mixing-path repairs.

- [x] **Step 1: Confirm the two WAVs and their formats**

Reconnaissance says 8-bit unsigned mono PCM, 22050 and 11025 Hz, with a trailing `LIST` chunk on the second. Verify from the files themselves before writing a parser against those assumptions, and confirm which WAVs the game actually loads (`grep` the tree; `PLAN.md` claims only two matter).

- [x] **Step 2: Write the parser**

A static `SDL_LoadWAV(char const *, SDL_AudioSpec *, Uint8 **, Uint32 *)` in `eSound.cpp`, guarded, using `fopen`. It must handle the RIFF/WAVE header, find `fmt ` and `data`, **skip unknown chunks** (that trailing `LIST` is why), and reject anything it does not understand rather than guessing. Populate the `SDL_AudioSpec` so `eSound.cpp:510-514`'s existing `AUDIO_U8` path applies.

Do **not** route through `SDL_RWops` — see landmine 3.

- [x] **Step 3: Replace the `Load()` guard, do not delete it**

M2's short-circuit exists because a throw from this path aborts the process (landmine 1). Replace it with a guard that fails the *load* without throwing — keep `loadError = true` on failure — so a missing or malformed WAV still cannot throw out of `fill_audio` → `Mix` → `Load()`.

- [x] **Step 4: `SDL_FreeWAV` → `free()`**

In `eCompat.cpp`. Leave `SDL_BuildAudioCVT` and `SDL_ConvertAudio` returning −1 and say in the comment that they are deliberately unreachable. `SDL_LoadWAV_RW` becomes deletable — delete it or comment why it stays.

- [x] **Step 5: Verify**

Build, run, and show the WAVs loading — a log line, a non-null pointer, the byte count matching the file's `data` chunk. Confirm the dedicated object is byte-identical and the dedicated wasm is still 2,488,298 bytes.

### Task 2: Make the mixing path correct

**Files:** Modify `src/engine/eSound.cpp`; possibly `web/webdefaults/autoexec.cfg`

**Interfaces:** Consumes Task 1. Produces **audible sound**.

Three repairs, all inherited from M2 and all documented in `PLAN.md`'s M3 note.

- [x] **Step 1: Retire silent voices**

`eSoundPlayer::Mix` does `return goon[viewer] = !wav->Mix(...)`, so with no data `goon` stays `true` forever instead of going false the way a finished sound does. Each such call also increments `real_sound_sources`, the input to the `loudness_thresh` voice limiter (`eSound.cpp:138-160`). Harmless while silent; a real bug the moment sound plays — which is now.

Note the limiter **has never run against real voices**. Watch it.

- [x] **Step 2: Make the `memset` conditional**

`fill_audio`'s `memset` must become conditional, **never deleted**. It exists because Emscripten hands back the same un-zeroed buffer every callback while every mixing path only *adds* into it. But `fill_audio` is also registered via `Mix_SetPostMix` (`eSound.cpp:270`), where the buffer already holds mixer output and zeroing would silence everything. That path is dead today (`#ifdef HAVE_LIBSDL_MIXER`, which nothing defines) — which is exactly why unconditional is safe *now* and stops being safe the moment anyone reaches for SDL_mixer.

- [x] **Step 3: Choose the buffer size deliberately**

`SOUND_BUFFER_SHIFT 3` in `autoexec.cfg` costs a measured **0.974 s** of latency; shift 0 gives **0.184 s** with no starvation, including through a real round. Pick a value, justify it, and record the measurement. If you change it, re-measure starvation yourself rather than trusting the recon number.

- [x] **Step 4: Verify audibly**

Sound has to actually come out. Assert **non-zero PCM reaching `pushAudio`** rather than "no errors" — silence and success look identical in a log. Say plainly that nobody has *heard* it; a waveform is evidence, an opinion about the mix is not.
