# M2 — Playable Single-Player vs AI

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Three complete rounds against three AI opponents, at ≥30 fps, in Chrome and Firefox — with the arrow keys actually steering.

**Architecture:** No new build targets and no new subsystems. M2 is a sequence of five runtime blockers between the menu and a running round, plus a keycode translation, plus the settings that make the gate mean what it says. Every fix is a guarded patch to existing source or an addition to `src/emscripten/eCompat.cpp`.

**Tech Stack:** Unchanged from M1 — Emscripten 6.0.8, SDL 1.2 emulation, WebGL 1 via `LEGACY_GL_EMULATION`, Asyncify.

## Global Constraints

- Every change to an existing game source file must be guarded: `#ifdef __EMSCRIPTEN__`, or `#if !defined(DEDICATED) && defined(__EMSCRIPTEN__)` where the file **also compiles into the dedicated build**. Check which applies before writing the guard — getting this wrong silently broke M0 during M1. The porting note's §1 tells you how to check, *and* documents that its own `awk` shortcut lies on `rScreen.cpp`; use the `em++ -E` or `llvm-nm` method it gives instead.
- **`make -f web/Makefile dedicated` must still produce a wasm of EXACTLY 2,488,298 bytes.** Verify at every task.
- **Do NOT add `-O2` (or any `-O`) to `CLIENT_LDFLAGS` during M2.** There is no `-O` at link today, which is the only reason `ASSERTIONS` is on — and assertions are the only reason blockers 3 and 4 announced themselves instead of producing silent garbage. Size work is M5's.
- **Never call `SDL_Delay` in the client.** Only call sleeps that appear in `ASYNCIFY_IMPORTS`. See porting note §8.
- New files ONLY under `src/emscripten/`, `web/`, `deps/`, `docs/`.
- Network protocol logic must never be deleted or stubbed.
- This repository has NO automated test suite and none is to be created. Verification is command-output and browser evidence.
- Toolchain: `source deps/emsdk/emsdk_env.sh`. `deps/*` and `web/node_modules` are symlinks to the main checkout — do not reinstall.
- Work happens in `.worktrees/m2-playable` on branch `m2-playable`. Commit after every green step.

## Known landmines — established by reconnaissance, do not rediscover

Reconnaissance **built and ran the client repeatedly**, fixing blockers in sequence to find the next one. Everything below marked *verified* was observed in a browser, not inferred. The full investigation is `.superpowers/m2-recon.md` (git-ignored).

1. **The round does not start today.** `sg_EnterGameCore` throws on its sixth line (`gGame.cpp:4543` → `eSound.cpp:417`) because `SDL_LoadWAV_RW` is a NULL-returning stub from M1. You get a "Sound Error" modal and bounce back to the menu. **Sound is M2's problem, not M3's**, and it blocks everything else. *Verified.*
2. **Five blockers, in sequence.** Each is only visible once the previous is fixed: (1) sound, (2) `SDL_ConvertSurface`, (3) `glDrawElements` with 32-bit indices, (4) an undiagnosed `numVertices must be an integer` at ~8.5 s, (5) keycodes — which does not crash anything but means you cannot steer. **Four of the five have nothing to do with `LEGACY_GL_EMULATION`.**
3. **M1's watch-list was four-for-four wrong.** Alpha test is fully implemented and already ran every M1 menu frame; fog is commented out (`gGame.cpp:1766-1772`); `GL_QUADS` is fine and the `GL_QUAD_STRIP` fix already landed in M1; the `GL_LUMINANCE` font atlas is unreachable because M1's texture patch covers it. Do not spend time there. `PLAN.md:27`'s "alpha-test tolerance" patch was never needed — two GL patches landed in M1, not three.
4. **`ASSERTIONS` is on and must stay on for this milestone.** See Global Constraints.
5. **`FIRST_USE 0` reaches the real main menu** (*verified, screenshot*) and also removes a per-frame `glFinish()` — but it **skips `sg_StartupPlayerMenu()`** (`gArmagetron.cpp:257-265`), which is the *only* code that loads any `keys_*.cfg`. Set it and you have a main menu with no key bindings at all. This plan therefore does **not** use it; see Task 7.
6. **`CONSOLE_LADDER_LOG 1` makes the gate machine-checkable.** `[L] NEW_ROUND` and `[L] ROUND_WINNER` reach `console.log`, and both existing drivers already capture console output. No build change needed. (Do **not** reach for `FS` — it is unexported and *aborts* on access.)
7. **Reconnaissance's own build skipped three `make`-generated files** (`config/aiplayers.cfg`, `language/languages.txt`, `resource/included/`), which yields **zero AIs**. Its "3D scene looked nearly empty" observation may be entirely that artifact. **Build with a real `make` before drawing any conclusion about what renders.**
8. **Firefox was never run during reconnaissance.** Every measurement is Chrome 152. The Firefox driver also never subscribed to browser-level WebGL warnings (porting note §9), so its clean M1 transcript is not evidence.
9. **`em++ -E` can fail silently — check its exit status.** Discovered in Task 1. Standalone `em++ -E` on `rScreen.cpp` intermittently exits 1 (`config.h` not found via `rSDL.h`) **while still emitting a large, plausible-looking preprocessed stream**, so any `grep -c` that does not test the exit code gets a confidently wrong answer. The porting note §1 recommends `em++ -E` as the authoritative guard-form check; treat that as "…and check `$?`". The reliable alternative Task 1 used: compile with `-c` using the real Makefile-derived flags and inspect the object with `llvm-nm`. Task 9 should fold this into the porting note.
10. **The binding menu renders blanks for every non-alphanumeric key.** `SDL_GetKeyName` in Emscripten returns names only for `a-z` and `0-9` (`libsdl.js:1754-1764`), so arrows, Escape, Enter, Tab and F-keys show as empty strings. Rebinding still works; it just shows nothing.

### Task 2: Make sound stop blocking the round

**Files:** Modify `src/engine/eSound.cpp`; possibly `src/emscripten/eCompat.cpp`

**Interfaces:** Consumes Task 1. Produces a client that **enters a round** — `[L] NEW_ROUND` in the console. Every remaining task depends on this.

M1's audio stubs return failure, and `eWavData::Load()` turns that into a thrown exception that aborts round entry. M2 ships silent; M3 owns real audio. This task only has to stop silence from being fatal.

- [ ] **Step 1: Reproduce the blocker, so you know what fixed means**

Build, serve, and drive the client into a round. You should see the "Sound Error" modal and a bounce back to the menu. Record the console output.

- [ ] **Step 2: Make `eWavData::Load()` fail quietly under Emscripten**

Reconnaissance assessed two shapes and recommended this one over making the stub succeed:

> Early-return with `loadError = true` under `__EMSCRIPTEN__`, because it closes all four entry points (`Mix`, `Reset`, `MakeGlobal`, and the loop constructor) — including the one that can fire from **inside an Asyncify rewind**. Emscripten registers `SDL.audio.queueNewAudioData` on `Asyncify.sleepCallbacks`, so `fill_audio` re-enters wasm after every unwind, and a C++ exception escaping there would be extremely unpleasant to debug.

Follow that reasoning unless you find it wrong — if you do, say so with evidence rather than silently choosing the other shape.

- [ ] **Step 3: Zero the audio buffer**

`fill_audio` (`eSound.cpp:92-119`) never initialises the buffer it is given, and Emscripten's `SDL_OpenAudio` `malloc`s it without zeroing. With no WAVs loaded nothing writes to it, so **uninitialised heap gets scheduled into the Web Audio graph** — audible garbage rather than silence. Add a `memset` at the top under the appropriate guard.

- [ ] **Step 4: Verify a round starts**

Add `CONSOLE_LADDER_LOG 1` to `web/webdefaults/autoexec.cfg` (Task 7 adds the rest), rebuild, and drive into a round:

```bash
grep -c "NEW_ROUND" /tmp/m2-t2/console.log   # expect ≥ 1
```

Report how far it gets — it will hit the next blocker, which is Task 3's.

- [ ] **Step 5: Verify the dedicated build, then commit**

### Task 3: `SDL_ConvertSurface` on a GL surface

**Files:** Modify `src/render/rTexture.cpp`

**Interfaces:** Consumes Task 2. Produces a round that survives cycle creation.

This one is genuinely surprising: Emscripten's `IMG_Load_RW` **nulls the surface's canvas** when the app uses OpenGL (`libsdl.js:2309-2312`, grep `we can free the canvas and context`), while `SDL_ConvertSurface` is implemented as a 2D canvas blit (`libsdl.js:1853-1866`). So `drawImage(null)` throws a JS `TypeError`.

The game reaches it once **per cycle, at every round start, on the default path**: `gCycle.cpp:2344-2349` builds a recoloured cycle texture, `rSurfaceTexture`'s constructor takes the surface by value (`rTexture.cpp:958-962`), and the copy runs `rSurface::CopyFrom` (`rTexture.cpp:360`).

It is a *JS* exception thrown inside a wasm import, so the game's `catch (tException const &)` handlers cannot catch it. It propagates through Asyncify's rewind and kills the game loop — black canvas, no further frames.

- [ ] **Step 1: Replace the conversion with a direct pixel copy**

The pixels are present — `IMG_Load_RW` calls `_SDL_LockSurface` precisely so they are. Under `#ifdef __EMSCRIPTEN__`, with the original preserved:

```cpp
SDL_Surface * o = other.surface_;
surface_ = SDL_CreateRGBSurface( SDL_SWSURFACE, o->w, o->h,
                                 o->format->BitsPerPixel,
                                 o->format->Rmask, o->format->Gmask,
                                 o->format->Bmask, o->format->Amask );
if ( surface_ && o->pixels && surface_->pixels )
    memcpy( surface_->pixels, o->pixels, o->h * o->pitch );
```

`SDL_CreateRGBSurface` with `SDL_SWSURFACE` does allocate a pixel buffer (`libsdl.js:365-367`).

- [ ] **Step 2: Handle the second call site**

`rTexture.cpp:329` has the same defect. It sits in the `default:` arm of the `BytesPerPixel` switch and is unreachable while surfaces are 32-bit — give it the same treatment, or an explicit comment saying why it is being left and what would make it live.

- [ ] **Step 3: Verify, then commit**

Drive into a round and confirm the black-canvas symptom is gone and the game proceeds. Report the new failure point — it should be Task 4's.

### Task 4: 32-bit indices in `glDrawElements`

**Files:** Modify `src/render/rModel.cpp`

**Interfaces:** Consumes Task 3. Produces a round that renders cycles.

`rModel::Render` (`rModel.cpp:332-335`) draws with `GL_UNSIGNED_INT` indices. Emscripten's client-array emulation handles only 16-bit indices and asserts otherwise (`libglemu.js:3528`). All three shipped cycle models take this path, every frame, per cycle. Observed: `Aborted(Assertion failed)` about 460 ms into the round.

- [ ] **Step 1: Take the immediate-mode branch**

Reconnaissance built and ran **both** candidate fixes and recommends this one:

> Forcing `modelTexFacesCoherent = false` takes the immediate-mode `glBegin(GL_TRIANGLES)` branch at `rModel.cpp:298-314`, which avoids Emscripten's *self-declared-broken* `prepareClientAttributes` path entirely. The alternative — converting indices to `unsigned short` — also works, but the immediate-mode variant is the more conservative choice.

Note both variants hit the same next blocker at the same elapsed time, so neither is implicated in it.

- [ ] **Step 2: Verify cycles render, then commit**

Screenshot the round. Report what is visible and what is not — and remember landmine #7: if the arena looks empty, check you built with a real `make` before concluding anything.

### Task 5: The undiagnosed `numVertices` abort

**Files:** Unknown until diagnosed

**Interfaces:** Consumes Task 4. Produces a round that survives longer than ~8.5 seconds.

**This is the one piece of genuine investigation in M2, and it is deliberately its own task.** With Tasks 2–4 fixed, the round runs for about 8.5 seconds and then aborts:

```
Assertion failed: `numVertices` must be an integer.
abort ← assert ← flush ← _emscripten_glEnd
```

That is `libglemu.js:3025-3028`. A non-integral result means a `glBegin`/`glEnd` block whose per-vertex attribute set **changed part-way through** — `addRendererComponent` grows the stride mid-batch, so the accumulated vertex counter no longer divides by the final stride. The likely shape is a batch where some vertices carry a texcoord or colour and others do not.

Reconnaissance confirmed it reproduces at the same elapsed time in both Task 4 variants, and did **not** identify the emitting call site.

- [ ] **Step 1: Get names on the stack**

Relink once with `-g2` in `CLIENT_LDFLAGS` (temporarily — remove it before committing) and reproduce. The abort stack should then name the C++ frame that called `glEnd`.

- [ ] **Step 2: Identify the mismatched batch**

Once you know the call site, find where the attribute set changes mid-batch. `rGLRender.cpp` is the funnel — `RenderEnd()`, `BeginPrimitive`/`End`, and the `TexCoord`/`Color` paths are the places a batch can acquire or lose a component.

If it turns out to be reachable only under a specific setting, say so — that may make it a configuration fix rather than a code one.

- [ ] **Step 3: Fix it, guarded, with the reasoning in the comment**

Escalate rather than improvise if the fix would require restructuring the renderer. A precise "here is exactly what happens and why the obvious fix is wrong" report is a better outcome than a guess.

- [ ] **Step 4: Verify the round survives well past 8.5 s, then commit**

Run for at least 60 seconds. Report how long it actually survived.

### Task 6: Make the arrow keys steer

**Files:** Modify `src/ui/uInput.cpp`

**Interfaces:** Consumes Task 5. Produces a client a human can actually play.

`config/keys_cursor.cfg` binds SDL 1.2's numeric keysyms for the arrows (273-276); Emscripten emits different values (1103-1106). Menus are unaffected because they use `SDLK_*` constants — which is exactly why M1 passed without noticing.

- [ ] **Step 1: Translate at config-parse time**

Reconnaissance assessed four options and recommends translation inside `tConfItem_key::ReadVal` (`uInput.cpp:120-141`), under `#if !defined(DEDICATED) && defined(__EMSCRIPTEN__)`, with a table mapping SDL 1.2's non-ASCII range onto this build's values (arrows 273-276, keypad 256-272, F-keys 282-296, Home/End/PgUp/PgDn 277-281, modifiers 300-308).

The reasons this is the honest fix, which belong in the comment:

- The `.cfg` files are **data** meaning "the left arrow key". 276 is SDL 1.2's encoding of that key; this build uses a different encoding for the same key. Re-encoding shipped data where it is read is exactly right.
- It fixes **all five** shipped layouts plus `default.cfg`'s camera and F-key bindings, in one place.
- **It is idempotent, and therefore M4-safe.** Source range (273-276, …) and target range (1103-1106, …) are disjoint, so re-reading a `user.cfg` that `WriteVal` wrote with 1104 passes through untouched. A player who rebinds in the menu gets 1104 saved and 1104 restored.

Rejected, with reasons worth recording: a shipped `keys_web.cfg` (only runs under `st_FirstUse`, so it dies the moment M4 persists a `user.cfg`); `KEYBOARD` lines in `autoexec.cfg` (works, but that file loads *after* `user.cfg`, making them hard overrides a player could never rebind away); defaulting to WASD (leaves the arrows dead, so a player who tries them concludes the game is broken).

**Only translate the non-ASCII range.** ASCII 0-127 already agrees and must be left alone.

- [ ] **Step 2: Verify steering works**

Drive the harness into a round and send arrow keys. The cycle must turn. Screenshot before and after a turn — a still image of a cycle proves nothing on its own.

- [ ] **Step 3: Verify the dedicated build, then commit**

- [ ] **Step 4: Decide on the binding menu, and say which you chose**

`keyname()` (`uInput.cpp:344-365`) will render blanks for arrows, Escape, Enter, Tab and F-keys, because Emscripten's `SDL_GetKeyName` only names `a-z` and `0-9`. Rebinding works; it just displays nothing.

This is a judgement call: it is UI polish, but it is also the screen a player uses to work around any binding problem M2 missed. Fix it with a small `keyname()` table under `__EMSCRIPTEN__`, or defer it to M4 with a note. Either is defensible — **state which you chose and why.**

### Task 7: The settings that make the gate mean something

**Files:** Modify `web/webdefaults/autoexec.cfg`

**Interfaces:** Consumes Task 6. Produces a client whose default game is three AIs and three rounds.

The game's default is **one** AI with an auto-adjusting count (`gGame.cpp:518-524`), so "three rounds vs three AIs" does not happen by itself.

- [ ] **Step 1: Add the gate settings**

```
SP_NUM_AIS 3
SP_AUTO_AIS 0
SP_LIMIT_ROUNDS 3
CONSOLE_LADDER_LOG 1
```

`SP_AUTO_AIS 0` matters: without it the game adjusts the AI count to the player's skill, so the gate would not reliably face three.

- [ ] **Step 2: Decide about `FIRST_USE`, and record the reasoning**

`FIRST_USE 0` reaches the real main menu directly and removes a per-frame `glFinish()`. **But it skips `sg_StartupPlayerMenu()`, the only code that loads any `keys_*.cfg`** — so with Task 6's translation in place you would have a main menu and no bindings at all, which is worse.

This plan's default is to **leave `FIRST_USE` alone** and have the gate drive through the first-run setup flow, which M1 already proved navigable. That is also what a real first-time visitor sees, which makes the evidence mean more.

If the setup flow turns out to obstruct the harness, `FIRST_USE 0` plus explicit `KEYBOARD` lines is the fallback — but note those become hard overrides under M4, so it is a stopgap, not a shipping answer. Record the per-frame `glFinish()` observation for M5 either way.

- [ ] **Step 3: Consider `CHATBOT_ALWAYS_ACTIVE 1`**

Reconnaissance believes this (`gCycle.cpp:2705-2720`) is the right way to get three *honest* rounds — the player cycle plays itself rather than sitting still and dying. It is **source-level only and unverified at runtime**. Try it; if it does not work, the gate will need the harness to steer, which is Task 8's problem.
